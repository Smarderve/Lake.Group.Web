# CMS V2 publishing — current milestone

Saving a page creates an immutable `ContentRevision` through `PUT /admin/v2/content/:key/draft` with optimistic revision matching. Creating a release calls `POST /admin/v2/releases` and stores a release record and snapshot artifact. The new snapshot carries forward verified documents from the current release, replacing only the selected document, so a later page release does not drop earlier published pages. A prior release can be restored over an existing draft as a new revision and release.

Editors must open the release review before creating a release. The review shows changed fields, warnings, and blockers. The backend repeats validation and rejects unsafe image, button, media, and canonical destinations, duplicate section keys, and attempts to publish a revision that is no longer the current draft.

The public adapter is connected on Home, About, Lake Aviation, Lake Oil and CSR. It derives the page key from the real route, verifies release identity and SHA-256 integrity before mutation, then applies the structured tree to existing production sections. It also resolves linked global values and renders published navigation. Pages retain static HTML when the release, document, schema or digest is unavailable or invalid.

CMS V2 artifacts use `public-content/cms-v2/`, separate from the existing website snapshot job's `public-content/current.json` and `public-content/releases/`. The storage adapter refuses to replace a legacy pointer if pointed at the wrong directory. Production must configure `CMS_V2_RELEASE_DIR` on durable storage reachable by the exporting backend instance, `CMS_V2_DEPLOYMENT_TOKEN` in both backend and GitHub Actions, and the existing release worker secrets. Concurrent releases across multiple backend writers still require deployment-level serialization.
